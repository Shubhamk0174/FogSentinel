SIMULATION 1. What is the core objective of the FogSentinel project?
▼
FogSentinel investigates two interconnected questions in IoT security:
  1. Detection: Can a machine-learning model accurately identify malicious IoT botnet traffic from high-dimensional statistical network features?
  2. Placement: What are the empirical, measured trade-offs in end-to-end response latency, WAN network bandwidth, and energy consumption when deploying this classifier locally on a Fog Gateway versus in a centralized Remote Cloud Datacenter?
DATASET 2. What represents "one record" in your dataset? Is it a raw network packet?
▼
No, a record is NOT a single packet or payload.
A record is a 115-dimensional vector of derived statistical metrics (packet stream weights, mean sizes, variance, standard deviation, packet jitter, covariance, and radii) computed over 5 rolling exponentially decaying time windows (λ = 0.01, 0.1, 1.0, 3.0, 5.0). Raw packet inspection at the edge is too noisy and compute-intensive; these statistical stream vectors capture temporal botnet flood behavior.
DATASET 3. What is the exact mathematical breakdown of the 115 features?
For each decaying window (λ ∈ {0.01, 0.1, 1, 3, 5}), the stream aggregator computes 23 continuous features:
  • Host-Level (H): Packet weight, mean packet size, variance from source IP (3 × 5 = 15 features).
  • Host-MAC-IP (MI): Packet weight, mean, variance between source IP and MAC (3 × 5 = 15 features).
  • Host-Host (HH): Traffic between specific source and destination IP sockets: weight, mean, std, packet jitter mean, and packet jitter std (7 × 5 = 35 features).
  • Host-Host Port (HpHp): Traffic to specific destination IP + port (7 × 5 = 35 features).
  • Multi-variate Properties: Covariance, Pearson correlation coefficient, and 2D spatial radius between streams (3 × 5 = 15 features).
Total Features = 23 statistical properties × 5 decay windows = 115 continuous dimensions
DATASET 4. Explain the 55-record demonstration dataset and how data leakage was prevented.
▼
The demonstration dataset is a balanced subset of 55 real records: 5 benign + 5 per each of the 10 attack classes (Mirai ack, scan, syn, udp, udpplain; BASHLITE combo, junk, scan, tcp, udp).

Zero Data Leakage Safeguards:
  1. The 55 demo records were extracted and isolated into data/demo/demo_features.csv (55 × 115) and data/demo/demo_labels.csv prior to any model training.
  2. Remaining data was partitioned using stratified sampling into Train (30,800), Validation (6,600), and Test (6,600).
  3. StandardScaler was fitted strictly on the Training set only. Validation, Test, and Demo data were strictly transformed using training parameters.
MACHINE LEARNING 5. What models did you evaluate, and why did Random Forest outperform Deep Learning?
▼
We evaluated three distinct model classes across Binary and 11-Class tasks: Logistic Regression (linear baseline), Multi-Layer Perceptron (feed-forward neural net with Dense(128) + ReLU + Dense(64)), and Random Forest (100 decision trees).

Held-Out Test Results (6,600 Records):
  • Random Forest: 99.98% Binary Acc (99.99% F1) | 99.98% Multi-Class Acc (99.98% F1) | 0.0066 ms latency.
  • MLP Neural Net: 99.97% Binary Acc | 90.71% Multi-Class Acc | 0.0154 ms latency.
  • Logistic Regression: 89.52% Binary Acc | 80.89% Multi-Class Acc.

Why Random Forest Won: Tabular statistical features naturally suit decision tree ensembles (Grinsztajn et al., NeurIPS). Abrupt packet-rate surges (e.g. UDP floods) produce step changes that decision trees segment with sharp orthogonal hyperplanes, whereas neural nets suffer from gradient smoothing and require significantly more tuning.
MACHINE LEARNING 6. What were the most discriminative features according to feature importance?
▼
Random Forest Gini importance analysis identified that packet jitter means and stream weights are the primary discriminators:
  • HH_jit_L0.1_mean (Importance: 0.0579) & HH_jit_L0.01_mean (0.0468): Inter-packet arrival jitter between host socket pairs. Normal human traffic has high, irregular jitter; automated botnet floods send packets with rigid, near-zero inter-arrival jitter.
  • H_L0.1_weight (0.0382) & H_L0.01_weight (0.0345): Source host packet counts per time window. Volumetric attacks abruptly multiply packet weights by orders of magnitude.
SIMULATION 7. What is iFogSim2, and does it train or execute your Python code?
▼
iFogSim2 does NOT execute or train Python machine learning models.
iFogSim2 is an open-source Java discrete-event simulation toolkit developed by the Cloudslab Laboratory (University of Melbourne) atop CloudSim. It models hardware topologies (MIPS capacity, RAM, power models), network links (bandwidth, propagation delay), and Distributed Data Flow (DDF) application graphs.

The Integration Bridge: Our script integration/export_workload.py profiled the Random Forest execution: 100 decision trees on 115 features requires ~1,000 MIPS of CPU work, a 960-byte input tuple (IOT_TRAFFIC), and a 168-byte output tuple (SECURITY_ALERT). iFogSim2 ingests this workload manifest to simulate execution at scale.
SIMULATION 8. How do you mathematically explain the latency difference (9.38 ms vs. 206.98 ms)?
▼
Total end-to-end response latency in iFogSim2 is modeled as:
Total Latency = T_prop(up) + T_trans(up) + T_queue + T_proc + T_prop(down) + T_trans(down)
  • Local Fog Placement: Traverses only the local 100 Mbps LAN link (2.0 ms propagation each way). With 1,000 MIPS processing effort on a 4,000 MIPS gateway:
    Latency ≈ 2.0 (LAN up) + 0.1 (trans) + 5.2 (queue + 0.25ms CPU) + 2.0 (LAN down) = 9.38 ms.
  • Remote Cloud Placement: Must traverse the physical WAN link twice (100 ms uplink + 100 ms downlink = 200 ms physical propagation delay):
    Latency ≈ 2.0 (LAN) + 100.0 (WAN up) + 0.9 (trans) + 2.1 (Cloud queue + CPU) + 100.0 (WAN down) + 2.0 (LAN) = 206.98 ms.

Fog placement eliminates the physical speed-of-light propagation bottleneck over hundreds of kilometers.
SIMULATION 9. What was the scope and result of the 48-scenario parameter sweep?
▼
We executed a full-factorial parameter sweep across 48 distinct configurations:
  • Device Counts (4): 10, 50, 100, 200 IoT devices.
  • Transmission Rates (2): 1.0 rec/s (light telemetry) vs. 5.0 rec/s (attack flood).
  • One-Way WAN Latencies (3): 25 ms (metro), 100 ms (internet), 200 ms (intercontinental).
  • Placements (2): Local Fog Gateway vs. Remote Cloud.

Key Sweep Findings:
  1. WAN Latency Decoupling: Fog placement latency remained invariant at ~9.38 ms across 25ms, 100ms, and 200ms WAN delays. Cloud latency scaled linearly: 56.98 ms → 206.98 ms → 406.98 ms.
  2. Bandwidth Elimination: Across all 24 Fog scenarios, WAN bandwidth was identically 0.00 KB. Cloud scenarios scaled up to 60,078 KB (60.1 MB).
CAVEAT 10. Does Fog placement always save energy compared to Cloud?
▼
No, Fog computing does not consistently save energy.
Our measured data shows that the Fog Gateway consumed slightly more energy in Fog placement (5,022.25 kJ vs 5,005.99 kJ) because its CPU was actively computing the 1,000 MIPS ML classification rather than idling. While Fog placement avoids WAN transmission power, commercial datacenters benefit from massive economies of scale and cooling efficiencies. Fog computing is justified by ultra-low latency, bandwidth savings, and offline survivability, not global energy reduction.
CAVEAT 11. Does FogSentinel physically disconnect devices or block switch ports?
▼
FogSentinel is an academic research prototype and simulation framework. Decisions are labeled as QUARANTINE_RECOMMENDED. In an actual physical deployment, this alert tuple would interface with a Software-Defined Networking (SDN) OpenFlow controller (such as OpenDaylight or ONOS) via REST APIs to dynamically push flow-drop rules to the network switch port.
SIMULATION 12. Why did you choose iFogSim2 instead of NS-3, Mininet, or OMNeT++?
▼
While NS-3, Mininet, and OMNeT++ specialize in packet-level Layer 2/3 protocol headers, routing tables, and radio frequencies, iFogSim2 is specifically engineered for Distributed Data Flow (DDF) application placement and edge-to-cloud mapping. It explicitly models CPU processing queues (MIPS), memory constraints, and linear power state models alongside network propagation delays. This allows us to directly test our core architectural question: where should the ML module execute?
